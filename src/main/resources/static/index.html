Aide utilisateur

Tout faire, dans l’ordre, sans surprise

Tu colles l’IP de ton VPS. L’agent lit ce serveur, puis n’installe que ce que tu confirmes. Aujourd’hui : un seul opérateur (toi), console en local. Plus tard (V9) : chacun sa session et ses paramètres. Ce qui est déjà posé sur cette machine n’est pas reproposé. Un autre VPS reprend les mêmes traitements depuis le début.

  1. 1. À quoi sert l’agent

    Tu as un VPS. Au lieu d’installer Docker, un reverse-proxy ou une base « à la main », tu passes par cet outil.

    • READ — lire (OS, CPU, RAM, logiciels). Automatique.
    • CHANGE — modifier (clé SSH, sécurité, Docker, Traefik, MariaDB, compte deploy, une app). Plan + tu confirmes.
    • DESTRUCTIVE — détruire. Refusé pour l’instant.

    L’IA ne reçoit jamais un accès root libre. Les scripts sont versionnés, pas inventés à la volée.

  2. 2. Ouvrir le cockpit et remplir les paramètres

    Menu Cockpit. Renseigne au minimum :

    • Hôte / IP — l’adresse de ton VPS
    • Utilisateur — souvent ubuntu, parfois root
    • Port — 22 sauf si tu l’as changé
    • Système — Auto convient

    Tant que tu n’as pas cliqué Analyser le VPS avec succès, le tableau reste vide. Pas de données d’exemple.

  3. 3. Clé SSH (obligatoire pour analyser)

    L’agent se présente avec une paire de clés : privée sur ce PC, publique sur le VPS (fichier ~/.ssh/authorized_keys).

    Piège OVH : « Mes clés SSH publiques » dans le compte n’installe rien sur un VPS déjà créé. Ça ne sert qu’à la création ou une réinstall. Ne réinstalle pas le serveur pour ça.

    Générer la clé une fois, sur ce PC (PowerShell) :

    ssh-keygen -t ed25519 -f $HOME\.ssh\vps-autopilot -C "vps-autopilot-personal" -N ""

    S’il demande d’écraser : n. Fichiers : vps-autopilot (secret) et vps-autopilot.pub (à coller sur le serveur).

    Clé déjà présente sur ce PC.

    Clé publique de cet agent (une seule ligne) :

    Chargement…

    Trois façons de la poser sur le VPS :

    A — Cockpit (le plus simple)

    1. IP + utilisateur (ubuntu ou root).
    2. Mot de passe du mail de livraison OVH.
    3. Installer la clé (CHANGE) → confirme.

    Le mot de passe n’est pas enregistré. Une ligne dans authorized_keys.

    B — Console KVM OVH

    Fiche du VPS (pas « Mes clés SSH ») → Console KVM → login mail, puis :

    mkdir -p ~/.ssh
chmod 700 ~/.ssh
touch ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
nano ~/.ssh/authorized_keys

    Colle la clé, une ligne. Enregistrer : Ctrl+O, Entrée, Ctrl+X.

    C — PowerShell

    ssh ubuntu@IP "mkdir -p ~/.ssh; chmod 700 ~/.ssh; touch ~/.ssh/authorized_keys; chmod 600 ~/.ssh/authorized_keys"
type $HOME\.ssh\vps-autopilot.pub | ssh ubuntu@IP "cat >> ~/.ssh/authorized_keys"

  4. 4. Analyser

    Bouton Analyser le VPS. L’empreinte SSH est enregistrée, puis lecture seule. Si « Authentification refusée » : la clé n’est pas sur ce compte — étape 3.

    Ensuite seulement : OS, CPU, RAM, disque, logiciels de ce VPS.

  5. 5. Choisir quoi installer (après l’analyse)

    La carte Installations (le bouton Installer) est juste sous le tableau. La liste « Que doit installer l’agent ? » est en dessous, dans un menu fermé : clique le titre pour déplier. Elle décrit ce que tu veux sur ce VPS, ce n’est pas le bouton.

    • Coche la section (Sécurité, Docker, Traefik, MariaDB, Compte deploy…). Ce menu décrit ce que tu veux. Le bouton Installer n’est pas dans les cases : il est dans la carte Installations, au-dessus.
    • Une nouvelle section par défaut (ex. Compte deploy) est ajoutée toute seule à une pile déjà enregistrée. Décocher reste possible et n’est pas recassé au rechargement.
    • Les détails (UFW, Compose, groupe docker…) sont dans un menu fermé. « 2 à installer » = encore cochés et pas détectés sur ce VPS → bouton Installer du composant dans Installations (pas dans ce menu).
    • Le pourquoi et ce que ça fera sont dans un second menu, fermé par défaut.
    • Déjà présent sur ce serveur : case grisée, mention « déjà installé », non recochable.
    • Décocher est permis. Si ça casse la politique (sécurité, Docker, Traefik, backups), tu es prévenu.
    • Redis est optionnel. Nginx sur l’hôte n’est pas proposé (risque webshell) : pas de case.
    • Rien n’est installé tant que tu n’as pas confirmé un CHANGE.

  6. 6. Bouton Installer

    • Il n’apparaît que dans la carte Installations, si le composant (ou un détail encore coché) manque sur ce VPS. Les actions READY sont en premier. Exemple : moteur Docker déjà là mais Compose / groupe docker encore cochés et non détectés → bouton Installer Docker (idempotent, ne réinstalle pas le moteur).
    • S’il est déjà conforme ici : pas de bouton, mention « déjà installé ». Une IP neuve reverra le bouton.
    • Exécutable aujourd’hui : Sécurité, Docker, Traefik, MariaDB, Compte deploy.
    • Sécurité n’est complète que si UFW est actif, fail2ban tourne, le mot de passe SSH est coupé et root SSH est fermé. fail2ban seul ne suffit pas.
    • Traefik et MariaDB : seulement après une sécurité complète sur ce VPS, et Docker présent. Traefik ouvre 80/443 sans exposer d’app. MariaDB n’écoute pas sur Internet.
    • Compte deploy : même prérequis. Utilisateur deploy, groupe docker, pas de sudo, clé de l’agent copiée. Aucune app n’est lancée.
    • Redis et backups : exécutables (Redis = conteneur ; backups = dump chiffré + copie locale). Une app simple : bande Applications. Un produit à plusieurs services : bande Plateformes (déclaration seulement pour l’instant).
    • Pendant analyse, clé ou install : un écran décrit le traitement. Ne ferme pas la page. Traefik / MariaDB : jusqu’à ~5 min (téléchargement d’image).
    • À la fin, une fenêtre indique succès ou échec (et pourquoi). Clique Fermer. En cas d’échec, l’état déjà connu du VPS n’est pas effacé.

    Ordre conseillé : clé SSH → analyser → sécurité → Docker → Traefik → MariaDB → compte deploy → app (Git).

  7. 7. Déployer une app

    • Avant Déployer : un popup liste ce qui sera fait. Liens publics en https://. Traefik installe toujours HTTPS (Let’s Encrypt) + redirection HTTP→HTTPS.
    • Domaine de base optionnel (ex. apps.mondomaine.com) : les apps deviennent https://my-bourse.apps.mondomaine.com. DNS * → IP du VPS. Sans domaine : fallback lab identifiant.<IP>.sslip.io (aussi en HTTPS).
    • Identifiant = slug court (my-bourse), pas le domaine. Nom d’hôte = DNS complet (my-bourse.apps.nebdev.org). Git = URL https://….
    • Sur chaque ligne de la liste : Modifier (remplit le formulaire), Supprimer (retire la ligne locale, sans arrêter le conteneur VPS), Déployer / Mettre à jour.
    • Premier test prévu : déployer ce produit (même dépôt, Dockerfile à la racine, port 8080, identifiant vps-autopilot). Il faut un Git HTTPS public (pousser ce dépôt). Nom d’hôte : DNS vers le VPS, ou un nom du type app.<IP>.sslip.io.
    • L’instance publique est cargo : page de preuve + /api/v1/health. Aucun CHANGE depuis Internet. Le cockpit reste sur 127.0.0.1:8088. Plus tard (V9) : cockpit en ligne derrière login, une session et des paramètres par opérateur.
    • Le DNS du nom d’hôte vers l’IP du VPS est à toi (sauf astuce sslip). Si MariaDB est déjà sur ce VPS : à chaque Déployer, une base + user SQL dédiés à l’app (db.env sur le serveur, hors git).

  8. 7b. Déclarer une plateforme (plusieurs services)

    • Pour un produit du type site + API (éventuellement admin, Redis, fichiers), utilise la bande Plateformes, pas trois apps 1:1 collées à la main.
    • Identifiant = slug du produit. Chaque service = un Git HTTPS, un port interne, des besoins (MariaDB, Redis, volume fichiers). Sous-dossier optionnel si le Dockerfile n’est pas à la racine du dépôt (monorepo).
    • DNS proposés : service.plateforme.ton-domaine. Variable de build typique : NEXT_PUBLIC_API_URL vers l’URL publique de l’API.
    • Enregistrer n’installe rien. Aucun SSH. Le déploiement groupé (deploy-platform) n’est pas encore livré.
    • Supprimer retire la fiche locale seulement.

  9. 8. Couleurs du tableau

    • Vert doux — présent / sain
    • Gris — absent (pas encore installé)
    • Ambre — inconnu
    • Rouge doux — à surveiller (SSH trop ouvert, pare-feu inactif, disque plein)

    Le tableau est découpé en bandes : État du serveur, Logiciels, Applications et plateformes, Pile et installations, Rapport. Filet à gauche, teintes calmes.

  10. 9. Ce que l’agent ne fera pas

    • Ouvrir le cockpit Installer/Déployer sur Internet sans login (cargo = preuve seulement ; plateforme multi-users = V9).
    • Cibler un serveur interdit ou déjà bloqué par l’agent.
    • Installer Apache, PHP ou Nginx directement sur l’hôte.
    • Lancer un shell root inventé par une IA.
    • Afficher un faux serveur (4 vCPU « démo ») à la place du tien.
